## 3. 項目 B: 秘密鍵 ACL の誤警告が消えたこと（#511）

第 4 回で報告された、**正常な構成の起動のたびに 3 リスナ分出ていた**次の警告が、**1 件も出ないこと**を確認する。

```
[ingestion-tls-private-key-grant-failed] …（理由: (null)）
[admin-https-private-key-grant-failed]  …（理由: (null)）
[viewer-https-private-key-grant-failed] …（理由: (null)）
```

### 手順

1. TLS 受信・管理リモート HTTPS・閲覧 HTTPS の 3 つとも、第 4 回と**同じく有効な状態**にする（= 権限が既に付いている状態。これが誤警告の出る条件だった）
2. サービスを再起動する
3. 起動直後のイベントログ / ログ出力から `private-key-grant-failed` を検索する

### 判定

| | 条件 |
|---|---|
| **合格** | `private-key-grant-failed` が **0 件** |
| **不合格** | 1 件でも出る → **全文と、そのときの秘密鍵の ACL（`icacls`）を報告** |

### 併せて 1 点（逆側の回帰確認）

**権限が付いていない状態からの起動では、従来どおり警告が出る**べきである。可能なら 1 つの証明書で ACL から `NT SERVICE\Yagura` を外して再起動し、次の 3 点を確認する（確認後は元に戻す）。

- 警告が出ること
- **理由が `(null)` ではなく実際の理由になっていること**
- 案内される `icacls` コマンドがそのまま通ること

**実施できない事情があれば省略してよい**——項目 B の主目的はあくまで「誤警告が消えたこと」である。

## 4. 項目 C: 昇格の 1 サイクル（#510 / #512）

**この項目は構成を変更する。以下の順で、バックアップを取ってから実施すること。**

現在この機器の保存先は SQL Server である。**いったん SQLite へ戻してから、あらためて昇格を実行**する。

### C-0. バックアップ（必須）

- `C:\ProgramData\Yagura` を丸ごと退避（第 4 回と同じ要領で日時付きディレクトリへ）
- 既存の SQL Server 側 DB（`YaguraLab2` 等）は**消さずに残す**

### C-1. SQLite へ戻す

1. サービスを停止する
2. 保存先設定を SQLite（ゼロ設定の既定）へ戻す
3. サービスを開始し、**UDP で syslog を 20〜30 件ほど投入**して、閲覧画面に出ることを確認する
   - ここでログを入れておくのは、次の保持期間削除に「消す対象」を持たせるため

### C-2. 保持期間を短く設定する

保持期間を**現実的に一番短い設定**にする（例: 1 日）。**この時点ではまだ削除が走らなくてよい。**

### C-3. 昇格を実行する ← 本項目の本番

管理画面の昇格ウィザードから SQL Server へ昇格する。

- 接続先: `localhost\SQLEXPRESS` / **新しい DB 名**（例: `YaguraLab3`）/ Windows 統合認証 / サーバ証明書を信頼する
- **「切替を実行」まで進める**（第 4 回は接続検証で止めた。本回は実行まで依頼する）

#### C-3-a. 観測点その 1 —— #512

**切替を実行した直後、まだサービスを再起動していない状態で**、管理ホームを開く。

- **期待**: 「**再起動待ちの変更**」のカードに、**保存先の切替が載っている**
- **記録**: カードのスクリーンショットまたは表示テキスト全文。**載っていない場合はその旨**（それが #512 の症状）

#### C-3-b. 観測点その 2 —— #510

続けて**サービスを再起動**し、**起動直後のログ**を確認する。

- **期待**: `[retention-catchup-query-failed]` が **出ない**
- **記録**: 起動から 3 分程度のログのうち `retention` を含む行を**すべて**。`catchup` 系が出た場合は**全文**
- あわせて、保持期間削除が実際に走ったか（`/status` の「通知・動作の記録」に「古いログの自動削除を実行」が出るか）も見る

### C-4. 後始末

**この状態のままでよい**（SQL Server 保存先に戻っているため）。元の `YaguraLab2` へ戻す必要はない。バックアップは残置する。

## 5. 項目 D: 拒否ダイアログの目視（Server 2016 / RDP）

第 4 回は WinRM 経由で対話デスクトップが無かったため、`/qb` のログから文面を全文取得した。**残っているのは「利用者の目に見える形」の最終確認だけ**である。

### 手順

1. `WIN-IVQ782H2OA4` (10.0.0.142) へ **RDP で接続**する（WinRM ではなく）
2. 項目 A で作った `Yagura-0.9.3-x64.msi` を転送する（SHA256 で転送後照合）
3. **エクスプローラから MSI をダブルクリック**する（通常の利用者と同じ経路）

### 記録

- **ダイアログのスクリーンショット**（これが本項目の成果物）
- 文面が**途中で切れていないか**——この文面は MSI の `LaunchCondition.Description` の 255 文字制限に合わせて詰めてあり、**実際のダイアログ幅で全文が読めるか**が確認したいこと
- 「OS ビルド 14393」と「17763 以上」の**両方の数字が読める**こと
- ダイアログを閉じた後、インストールされていないこと（`Program Files\Yagura`・サービス・ARP エントリ）

### 後始末

転送した MSI は削除する。
